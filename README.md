# 班守 ShiftGuard

**醫護排班治理平台 ／ 模組一：臨時缺班替補**

當醫護人員臨時請假，這個平台在幾秒內給出合格的替補候選人、排序理由與風險提示——並且每一個判斷都交代得出依據。

## 快速開始

**線上版（免安裝）**：

- 平台：https://bobyu89.github.io/nursing-agent/
- 引擎測試：https://bobyu89.github.io/nursing-agent/tests.html

或本機執行：

```bash
git clone https://github.com/bobyu89/nursing-agent.git
cd nursing-agent
```

直接**雙擊 `index.html`** 就能跑。無需安裝、無需編譯、無需網路。
線上版與本機版行為完全相同（mock 模式本來就不需要網路）；每次 push 後 GitHub Pages 會自動更新。

若偏好本機伺服器：

```bash
python -m http.server 8777
```

然後開啟 http://localhost:8777。

### 三分鐘試一遍

1. 第一頁的訊息框可以直接改寫。試著把內容換成「我下週三大夜要去進修」，按下解析——系統會算出日期與班別，並追問訊息裡沒寫的單位與資格。
2. 按「確認缺班條件，開始尋找替補」。
3. 展開任一位候選人的**評分卡**，看見每一分是怎麼來的。
4. 到「規則庫」把 S1 公平性權重從 30 拉到 0，按重新計算——排序會當場改變。

## 這是什麼

醫院班表排定後，仍會因臨時請假、進修或緊急任務產生缺班。護理長必須在很短的時間內確認：誰具備必要資格、當天能不能支援、工時與休息時間合不合規、替補後會不會影響其他班別。

但真正讓這件事難的不是速度——**是找人的標準說不清楚，事後交代不了為什麼是找你不是找他。** 結果往往是「找最好講話的那個」，而這正是護理職場離職的真實原因之一。

所以這個平台的價值主張是三件事，缺一不可：

| | 沒有它會怎樣 |
|---|---|
| **快** | 缺班補不上，照護人力不足 |
| **合規** | 補上了卻違反工時規範，變成勞檢與病安風險 |
| **公平可解釋** | 補上了也合規，但持續壓在同一批人身上，最後是離職 |

只做「快」的話，Excel 篩選就夠了。**平台存在的理由是後面兩件事。**

## 核心設計原則：確定性歸程式、語言歸模型

| | 由誰負責 | 內容 |
|---|---|---|
| **算得準** | 規則引擎（確定性程式碼） | 工時累計、班間休息時數、連續上班天數、證照效期比對、加權評分 |
| **說得清** | 語言模型 | 解析請假訊息、追問缺漏條件、把數字寫成人話、生成主管摘要與通知草稿 |

算錯工時在醫療場域是合規事故，不是體驗瑕疵。語言模型會產生流暢但錯誤的數字，這在這個場景不可接受；反過來，規則引擎寫不出讓護理長願意讀的句子。

**Agent 不會做的事**：不自行補完訊息中沒寫的欄位（改為追問）、不改寫規則引擎算出的數字、不自行放寬任何規則、不代替主管決定。

## 七個畫面

| # | 畫面 | 看點 |
|---|---|---|
| 1 | 缺班事件 | 貼上請假訊息 → 解析；**訊息沒寫的欄位主動追問，不臆測** |
| 2 | 替補候選人 | 合格候選排序 + **不推薦名單逐筆標明規則代碼與原因** |
| 3 | 主管確認 | 替補後班表變化、人工確認事項、**通知草稿停在草稿** |
| 4 | 公平性與留痕 | 分配狀況即時更新、每一步操作留痕 |
| 5 | 班表與人員 | 三份輸入資料：人員主檔、1 週班表、請假紀錄 |
| 6 | 規則庫 | 調整門檻與權重，決策結果即時重算 |
| 7 | 多筆缺班 | **逐筆指派 vs 全局指派對照**：稀缺人力被逐筆貪心用掉時，全局指派仍能全數補滿 |

### 兩筆最有說服力的排除

| 人員 | 班表上當日狀態 | 為什麼不能用 |
|---|---|---|
| **N-07** | 8/09「沒有班」 | 8/08 大夜要到 8/09 早上 **07:00** 才下班，白班 07:00 開始 → **班間休息 0 小時** |
| **N-09** | 8/09「沒有班」 | 已連續上班 8/03–8/08 共 **6 天**，替補後變 7 天 |

兩人資格完全符合，用 Excel 篩「當天沒班的人」都會被選出來。這就是規則引擎存在的意義。

## 規則庫

### 硬性約束（違反即排除）

| 代碼 | 規則 | 依據 |
|---|---|---|
| H1 | 職務與資格符合，證照在效期內 | 院內護理人員資格管理辦法 |
| H2 | 當日未排其他班別 | 院內排班作業規範 |
| H3 | 非請假／不可排班狀態 | 院內請假管理規定 |
| H4 | 班間休息 ≥ 11 小時 | 勞基法第 34 條 |
| H5 | 連續上班 ≤ 6 天 | 勞基法第 36 條 |
| H6 | 週工時 ≤ 60 小時 | 勞基法第 32 條 |

### 軟性偏好（加權評分，總分 100）

| 代碼 | 構面 | 權重 |
|---|---|---|
| S1 | 班別分配公平性 | 30 |
| S2 | 工時餘裕 | 25 |
| S3 | 班別型態相符 | 20 |
| S4 | 可支援意願 | 15 |
| S5 | 單位熟悉度 | 10 |

### 風險標記（不排除，但主管必須知情）

F1 週工時超過 48 小時軟性上限（需額外核准）／F2 連續上班達 5 天／F3 跨單位支援／F4 近期替補次數偏高

## 測試

「確定性歸程式」的前提是程式算得對。**雙擊 `tests.html`** 即可離線執行引擎測試，
釘住合規事故等級的邊界條件：

- 班間休息剛好 11 小時（過）與 10.5 小時（不過）、大夜接白班間隔 0 小時
- 連續上班第 6 天（過）與第 7 天（不過）
- 週工時一律以**缺班日所在的自然週**計算——下週的缺班不會誤算本週的工時
- Demo 資料集的完整結果（4 位候選、7 位排除、排除原因逐筆比對）
- 訊息解析不臆測：沒有時間線索就不給日期，「下下禮拜三」不會被當成下禮拜三，缺漏欄位全數轉為追問

同一份測試也會在 **GitHub Actions** 上以 Node 自動執行（`tests/run-node.js`），
每次 push 都會重新驗證；本機不需要安裝任何東西。

引擎以 `createEngine(db)` 建立，人員／班表／規則皆由外部注入，
同一份程式碼可在瀏覽器、測試頁與未來的 Lambda 端點上運行。
所有計算背後的語義定義（自然週怎麼算、連續天數怎麼定義、缺班事件的生命週期）
集中在 [docs/CONTEXT.md](docs/CONTEXT.md)——文件與程式不一致時，以文件為準修程式。

## 關於 LLM 模式

轉接層有兩種模式，畫面右上角永遠標示目前跑在哪一種：

- **`mock`（預設）** — 以關鍵詞規則實際比對輸入文字，改寫訊息結果會跟著變。**不是預錄腳本**，但理解能力弱於真實模型。離線可跑，確保現場不因網路或額度中斷。
- **`api`** — 接真實模型（AWS Bedrock 或相容端點），需設定 `LLM.endpoint`。
  任何一次呼叫失敗（斷網、額度、端點錯誤）都會**自動退回 mock 並在畫面標示**，演示不中斷。

規則庫的調整會自動保存在本機瀏覽器（localStorage），重新整理不會遺失；
「還原預設規則」可回到出廠設定。上場演示流程與逐幕台詞見 [docs/DEMO-SCRIPT.md](docs/DEMO-SCRIPT.md)。
