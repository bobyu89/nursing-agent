# 班守 ShiftGuard — 提案素材

> 職游 NaviCareer × AWS × 伊雲谷｜AI 職涯實戰營 DEMO DAY
> 第 4 組　題目（三）醫療服務 — AI 醫護臨時缺班替補 Agent
> 簡報對象：護理部主管、人資主管、醫療營運主管、院區管理者

---

## 一、我們對這道題的判斷

命題描述的痛點是「主管必須在短時間內確認誰有資格、能不能支援、工時合不合規」。但我們認為，真正讓這件事難的不是速度——**是找人的標準說不清楚，事後交代不了為什麼是找你不是找他。**

護理長心裡其實有一套規則：誰的證照還在效期、誰昨天上大夜、誰這個月已經被叫過三次。問題是這套規則只存在她腦子裡。所以結果往往是「找最好講話的那個」，而這正是護理職場離職的真實原因之一。

因此我們的價值主張是三件事，缺一不可：

| | 沒有它會怎樣 |
|---|---|
| **快** | 缺班補不上，照護人力不足 |
| **合規** | 補上了卻違反工時規範，變成勞檢與病安風險 |
| **公平可解釋** | 補上了也合規，但持續壓在同一批人身上，最後是離職 |

只做「快」的話，Excel 篩選就夠了。**平台存在的理由是後面兩件事。**

## 二、產品定位

**班守 ShiftGuard —— 醫護排班治理平台。**

第一個模組，也是本次唯一實作的模組：**臨時缺班替補決策**。

我們刻意不做完整月班表重排（命題亦明文排除）。介面、資料模型與規則庫都以平台方式設計，讓這個模組可以直接長成後續的排班治理系統，但今天交付的是一個做完、做透的模組，不是一個做了一半的大平台。

---

## 三、核心設計原則：確定性歸程式、語言歸模型

這是整個提案最重要的一句話。

| | 由誰負責 | 內容 |
|---|---|---|
| **算得準** | 規則引擎（確定性程式碼） | 工時累計、班間休息時數、連續上班天數、證照效期比對、加權評分 |
| **說得清** | 語言模型 | 解析請假訊息、追問缺漏條件、把數字寫成人話、生成主管摘要與通知草稿 |

**為什麼要這樣切？** 因為算錯工時在醫療場域是合規事故，不是體驗瑕疵。語言模型會產生流暢但錯誤的數字，這在這個場景是不可接受的風險。反過來，規則引擎寫不出讓護理長願意讀的句子。

這也直接回應命題要求的「區分資料事實與模型推測」：畫面上每一個數字都可回溯到規則引擎的計算，每一段敘述都標明是模型生成。

**Agent 不會做的事**：不自行補完訊息中沒寫的欄位（改為追問）、不改寫規則引擎算出的數字、不代替主管決定。

## 四、系統架構

```
[護理長] 貼上請假訊息
     │
     ▼
┌─────────────────────────────────────────────┐
│ ① 事件理解層（語言模型）                      │
│    自然語言 → 結構化缺班事件                   │
│    欄位不足 → 主動追問，絕不臆測                │
└─────────────────────────────────────────────┘
     │  缺班事件（日期／班別／單位／必要資格）
     ▼
┌─────────────────────────────────────────────┐
│ ② 規則庫 Rule Registry                       │
│    硬性約束 H1–H6 ／ 軟性偏好 S1–S5 ／ 風險 F1–F4 │
│    ★ 規則是「資料」，主管可自行維護              │
└─────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────┐
│ ③ 決策引擎（確定性運算，無模型參與）            │
│    硬性篩選 → 排除 + 原因                      │
│    軟性評分 → 排序 + 評分卡                    │
│    風險偵測 → 標記 + 是否需額外核准             │
└─────────────────────────────────────────────┘
     │
     ▼
┌─────────────────────────────────────────────┐
│ ④ 治理層                                     │
│    主管確認摘要 ／ 通知草稿（不自動發送）        │
│    公平性儀表板 ／ 決策留痕 Audit Log          │
└─────────────────────────────────────────────┘
     │
     ▼
[授權主管] 決定 → 於院內系統完成正式調班
```

### 雲端架構（AWS）

| 層 | 服務 | 說明 |
|---|---|---|
| 前端 | Amazon S3 + CloudFront | 靜態網頁託管 |
| API | Amazon API Gateway + AWS Lambda | 決策引擎與轉接層 |
| 模型 | **Amazon Bedrock** | 事件解析、理由生成、摘要與草稿 |
| 資料 | Amazon DynamoDB | 人員主檔、班表、請假、規則庫、Audit Log |
| 稽核 | Amazon CloudWatch Logs | 決策留痕與存取軌跡 |
| 權限 | AWS IAM + Cognito | 主管／管理員角色分離 |

> **DEMO 版本說明**：現場展示為純前端版本，語言模型轉接層預設跑在 `mock`（模擬）模式，畫面右上角會標示，簡報時亦會主動說明。mock 模式**不是預錄腳本**——它以關鍵詞規則實際比對輸入文字，改寫訊息結果會跟著改變，只是理解能力弱於真實模型。這樣安排是為了確保現場不因網路或額度中斷。上表為正式導入架構。

## 五、規則庫設計

### 硬性約束（違反即排除）

| 代碼 | 規則 | 依據 |
|---|---|---|
| H1 | 職務與資格符合，證照在效期內 | 院內護理人員資格管理辦法 |
| H2 | 當日未排其他班別 | 院內排班作業規範 |
| H3 | 非請假／不可排班狀態 | 院內請假管理規定 |
| H4 | 班間休息 ≥ 11 小時 | 勞基法第 34 條 |
| H5 | 連續上班 ≤ 6 天 | 勞基法第 36 條 |
| H6 | 週工時 ≤ 60 小時 | 勞基法第 32 條 |

### 軟性偏好（加權評分，總分 100）

| 代碼 | 構面 | 權重 | 為什麼要有這條 |
|---|---|---|---|
| S1 | 班別分配公平性 | 30 | **避免「誰好講話就一直找誰」，本平台最重要的治理訊號** |
| S2 | 工時餘裕 | 25 | 優先分配給工時仍有空間者，降低過勞 |
| S3 | 班別型態相符 | 20 | 不打亂人員既有生理作息 |
| S4 | 可支援意願 | 15 | 尊重意願，提高實際應允率 |
| S5 | 單位熟悉度 | 10 | 降低跨單位交接風險 |

### 風險標記（不排除，但主管必須知情）

F1 週工時超過 48 小時軟性上限（需額外核准）／F2 連續上班達 5 天／F3 跨單位支援／F4 近期替補次數偏高

## 六、DEMO 動線與看點

| # | 畫面 | 看點 |
|---|---|---|
| 1 | 缺班事件 | 貼上 LINE 訊息 → 解析出日期、班別、原因；**單位與必要資格訊息沒寫，Agent 主動追問而非臆測** |
| 2 | 替補候選人 | 4 位合格候選 + **7 位不推薦名單，逐筆標明規則代碼與原因** |
| 3 | 評分卡 | **本場高光**：攤開五個構面的得分與依據 |
| 4 | 主管確認 | 替補後班表變化、人工確認事項、**通知草稿停在草稿** |
| 5 | 公平性與留痕 | 分配狀況即時更新、每一步操作留痕 |
| 6 | 規則庫 | 現場把 S1 權重從 30 拉到 0 → **排序當場改變**，證明規則是活的 |

### 三個可以接受現場挑戰的地方

**① 評審可以自己改寫訊息。** 輸入框是活的：日期、班別、事由、單位、資格都從文字內容比對而來。試著輸入「我下週三大夜要去進修」→ 系統會算出 8/19（三）大夜、進修，並追問單位與資格；輸入「我不能上班了」→ 四項欄位全部轉為追問，Agent 一項都不臆測。

**② 找不到人的時候怎麼辦。** 若合格候選人不足 3 位，系統會列出「放寬哪一條規則會多出誰」的試算，並明確區分：H3 請假可由主管徵詢當事人意願（可評估），H4／H5／H6 是勞基法下限、H1 是病安底線（不建議放寬，僅供了解缺口成因）。另外提供四項不涉及鬆綁規則的處理方式，包含通報護理部調度中心。**Agent 不會自行放寬任何規則。**

**③ 可以連續處理第二筆缺班。** 主管確認後，替補班次會寫回班表、替補次數會累計。接著處理同日第二筆缺班時，剛才被指派的人會因「當日已排白班」被 H2 自動排除，公平性分數也已下降。治理迴路是閉合的，不是畫面上的裝飾。

### 最有說服力的兩筆排除

| 人員 | 班表上當日狀態 | 為什麼不能用 |
|---|---|---|
| **N-07** | 8/09「沒有班」 | 8/08 大夜要到 8/09 早上 **07:00** 才下班，白班 07:00 開始 → **班間休息 0 小時** |
| **N-09** | 8/09「沒有班」 | 已連續上班 8/03–8/08 共 **6 天**，替補後變 7 天 |

兩人資格完全符合，用 Excel 篩「當天沒班的人」都會被選出來。**這就是規則引擎存在的意義**，也是我們回答「這用試算表做不到嗎」的答案。

## 七、資料準備與假設

**全部為虛構模擬資料**，人員一律代號化（N-01 ~ N-11），不使用任何真實或虛構姓名，不含病患資料、病歷或可識別個人之內容。

| 項目 | 內容 |
|---|---|
| 人員 | 11 名（命題要求 8–12 名） |
| 每人欄位 | 職務、資格與證照效期、可支援班別、所屬與熟悉單位、近 30 天替補次數、休假狀態 |
| 班表 | 1 週（2026-08-03 ~ 08-09），三種班別 D／E／N，各 8 小時 |
| 缺班事件 | 1 件：2026-08-09（日）白班，內科病房 3A，需 ACLS + 化療給藥資格 |
| 規則 | 硬性 6 條、軟性 5 條、風險標記 4 條，皆可於介面調整 |

**主要假設**：每班固定 8 小時；週工時以自然週計；「連續上班天數」以有排班之日期連續計算；公平性以近 30 天替補次數為代理指標（正式導入應改用院內實際叫班紀錄）。

## 九、導入路線圖

| 階段 | 內容 |
|---|---|
| **第一階段（本次交付）** | 單一缺班事件的替補建議、規則庫、公平性儀表板、決策留痕 |
| 第二階段 | 串接院內 HIS／HR 系統；改用真實叫班紀錄計算公平性；主管行動裝置推播 |
| 第三階段 | 月班表產生器（沿用同一套規則庫）；缺班熱點分析；人力配置預警 |
| 第四階段 | 跨單位人力調度、以歷史留痕回饋調整規則權重 |

規則庫從第一階段就是共用的：第三階段的月班表產生器不需要重寫規則，直接沿用同一份資料。**這是我們一開始就把它設計成「資料」而不是「程式碼」的原因。**

## 十、執行方式

雙擊 `index.html` 即可執行，無需安裝、無需編譯、無需網路。

若要以本機伺服器執行：

```bash
python -m http.server 8777
```

檔案結構：

```
index.html            六個畫面
assets/styles.css     樣式
src/data.js           模擬資料（人員／班表／請假／缺班事件）
src/rules.js          規則庫
src/engine.js         確定性決策引擎
src/llm.js            語言模型轉接層（mock／api）
src/app.js            畫面渲染與流程
docs/proposal.md      本文件
```
