# CONTEXT — 領域語義定義

這份文件是本專案的**權威語義定義**：規則引擎算出的每一個數字，背後的定義都在這裡。
文件與程式行為不一致時，以本文件為準修程式（並補測試）；要改定義，先改這裡。
`tests/engine.test.js` 是這些定義的可執行版本。

## 核心詞彙

| 詞彙 | 定義 |
|---|---|
| **缺班事件（Gap）** | 一筆「某日、某班別、某單位、需某些資格」的人力缺口。由通報訊息解析＋主管補充而成。 |
| **候選人（Candidate）** | 通過**全部**啟用中硬性約束（H1–H6）的人員，依軟性評分排序。 |
| **排除（Excluded）** | 違反任一硬性約束的人員；每筆排除必附規則代碼與原因。原班人員一律排除（代碼 `—`）。 |
| **寫回（Apply）** | 主管確認後，替補班次寫入班表、該員替補次數 +1。這讓同日第二筆缺班的評估看得到新狀態。 |
| **規則庫（Rule Registry）** | 硬性約束 H、軟性偏好 S、風險標記 F。規則是可維護的資料，不是寫死的程式碼。 |

## 時間語義

- **自然週**：週一 00:00 起至週日 24:00。週工時（H6、S2）一律以**缺班日所在的自然週**計算，
  與示範資料涵蓋哪一週無關。
- **班次工時歸屬**：整段班次工時歸屬**班次起始日**所在之週。大夜（23:00–翌日 07:00）
  雖有 7 小時落在隔日，仍全數計入起始日。
- **連續上班天數**：以「班次起始日」為單位連續計算，含缺班日本身，向前、向後展開。
  大夜下班日（翌日早晨）**不**另計為一個上班日——它對次日的影響由 H4 班間休息負責衡量。
- **班間休息（H4）**：以班次**實際起訖時刻**計算與前後班次的間隔，大夜跨日已納入。
  門檻為「≥ 11 小時」，恰好 11 小時視為合格。
- **請假粒度**：以「日」為最小單位。半天假、時段假不在本版範圍，一律視為全日不可排班。

## 法規對應與院內政策聲明

| 規則 | 性質 | 說明 |
|---|---|---|
| H4 班間休息 ≥ 11 小時 | 法定下限 | 勞基法第 34 條（輪班換班間距）。 |
| H5 連續上班 ≤ 6 天 | **院內政策（比法規更嚴）** | 勞基法第 36 條為「每七日一例假」；醫療業於變形工時制度下，合法連續上班可能超過 6 天。本平台採更嚴格的固定上限作為預設治理政策。 |
| H6 週工時 ≤ 60 小時 | **院內政策（簡化模型）** | 勞基法第 32 條規範的是延長工時上限，非單週總工時常數。60 小時為「正常 40 ＋ 延長 20」的簡化絕對上限。正式導入時應依院方適用之（二週／四週／八週）變形工時制度重新定義。 |

> 對外簡報時：H4 可稱法定下限；H5、H6 應稱「以法規為底線、比法規更嚴的院內治理政策」。

## 單位人力與護病比

`UNIT_MIN_STAFF` 定義各單位每班別的**最低配置人力**；主管確認摘要會顯示
「目前在班 → 替補後」與配置的比對，替補後仍不足時列入人工確認事項。
本 demo 的班表是單位的**部分名單**，故最低配置以 1 計，用來呈現判定機制本身；
正式導入時應對接院內護病比（nurse-to-patient ratio）與實際配置人數，
並將「替補後單位人力仍不足」升級為明確的風險標記。

## 決策留痕的防竄改

留痕採**雜湊鏈結**（每筆紀錄的雜湊包含前一筆的雜湊），事後修改任一筆
都會使後續整條鏈驗證失敗；匯出檔含 `chainValid` 驗證結果。
此為前端 demo 可誠實實作的 tamper-evident 機制；正式導入時由後端以
append-only 方式儲存，雜湊鏈可保留作為跨系統核對的輕量證據。

## 多筆缺班的指派語義

- **逐筆指派（貪心，對照組）**：依缺班順序每筆取當下最高分候選並立即寫回模擬班表。
- **全局指派**：枚舉所有可行組合（每筆可指派或留空），目標為字典序最佳化——
  **先「填補筆數最多」、再「總分最高」**；同分取先枚舉之組合（結果確定性）。
- 組合可行性以完整模擬驗證：同一人接多筆時，前一筆寫回後會影響後一筆的
  H2／H4／H5／H6 判定與評分（工時、公平性累計）。
- 規模聲明：demo 為 11 人 × 少量缺班，暴力枚舉即為最佳解；正式導入若缺班筆數
  放大，應改用匹配／整數規劃求解器，目標函數不變。
- 指派結果是**建議**：仍需主管逐筆確認後才寫回正式班表。

## 公平性訊號

`standbyCount30d`（近 30 天被叫班次數）在本版為**靜態快照的代理指標**：寫回時 +1，
但不會隨時間滾動過期。正式導入應定義為「以院內實際叫班紀錄計算之滾動 30 天窗口」。
S1 飽和門檻（預設 5 次）意義：達此次數者公平性得 0 分，優先保護已被頻繁叫班的人。

## 缺班事件生命週期

```
草稿（解析中） → 已確認條件（評估中，可重算、可換人選） → 已結案（主管確認、已寫回）
```

- **已結案的事件是不可變的**：不得重新選人、不得重算——替補班次已寫回班表，
  重算會讓剛指派的人被 H2 排除，產生「已補完卻顯示缺口」的矛盾。
- 結案後的規則調整仍會儲存，**套用於下一筆缺班評估**。
- 要重新評估，回「缺班事件」頁重新確認條件，即建立新的評估。

## mock 解析的能力邊界（不臆測原則）

mock 模式以關鍵詞規則比對訊息，**只回報有依據的欄位**，其餘轉為追問：

- 日期：支援「今天／明天／後天」「M/D、M月D日」「（下×N）禮拜／週／星期＋X」
  （每一個「下」往後一週：下下禮拜三 = +14 天）。無法明確換算的說法（「這週末」「連兩天」）→ 追問。
  訊息中出現**多個時間線索且指向不同日期**（例：「從今天開始發燒，禮拜天的班……」）→
  不挑選其中一個，標記為模糊、轉為追問，並列出偵測到的所有線索。指向同一天則正常解析。
- 班別：白班／早班／日班、小夜／晚班、大夜／夜班。
- 事由：病假、進修、事假、特休關鍵詞；無線索時記為「臨時請假」（唯一有預設值的欄位）。
- 單位與必要資格：僅在訊息明確提及時抽取，否則一律追問。

模型（mock 或 api）**永遠不做**：補完缺漏欄位、改寫引擎算出的數字、放寬規則、代替主管決定。

## 引擎介面

引擎以 `createEngine(db)` 建立，人員／班表／班別／職級／規則全部由外部注入，
引擎內不讀取任何全域資料。注入的是同一份參照：規則庫調整與寫回即時生效。
同一份 `src/engine.js` 在瀏覽器（index.html）、測試（tests.html 與 CI 的 Node runner）
與未來的 Lambda 端點上運行，行為必須一致——這由 `tests/engine.test.js` 保證。
