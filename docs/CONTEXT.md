# CONTEXT — 領域語義定義

這份文件是本專案的**權威語義定義**：規則引擎算出的每一個數字，背後的定義都在這裡。
文件與程式行為不一致時，以本文件為準修程式（並補測試）；要改定義，先改這裡。
`tests/engine.test.js` 是這些定義的可執行版本。

## 核心詞彙

| 詞彙 | 定義 |
|---|---|
| **缺班事件（Gap）** | 一筆「某日、某班別、某單位、需某些資格」的人力缺口。由通報訊息解析＋主管補充而成。 |
| **候選人（Candidate）** | 通過**全部**啟用中硬性約束（H1–H6）的人員，依軟性評分排序。 |
| **排除（Excluded）** | 違反任一硬性約束的人員；每筆排除必附規則代碼與原因。原班人員一律排除（代碼 `—`）。 |
| **寫回（Apply）** | 主管確認後，替補班次寫入班表、該員替補次數 +1。這讓同日第二筆缺班的評估看得到新狀態。 |
| **規則庫（Rule Registry）** | 硬性約束 H、軟性偏好 S、風險標記 F。規則是可維護的資料，不是寫死的程式碼。 |

## 時間語義

- **自然週**：週一 00:00 起至週日 24:00。週工時（H6、S2）一律以**缺班日所在的自然週**計算，
  與示範資料涵蓋哪一週無關。
- **班次工時歸屬**：整段班次工時歸屬**班次起始日**所在之週。大夜（23:00–翌日 07:00）
  雖有 7 小時落在隔日，仍全數計入起始日。
- **連續上班天數**：以「班次起始日」為單位連續計算，含缺班日本身，向前、向後展開。
  大夜下班日（翌日早晨）**不**另計為一個上班日——它對次日的影響由 H4 班間休息負責衡量。
- **班間休息（H4）**：以班次**實際起訖時刻**計算與前後班次的間隔，大夜跨日已納入。
  門檻為「≥ 11 小時」，恰好 11 小時視為合格。
- **請假粒度**：以「日」為最小單位。半天假、時段假不在本版範圍，一律視為全日不可排班。

## 法規對應與院內政策聲明

| 規則 | 性質 | 說明 |
|---|---|---|
| H4 班間休息 ≥ 11 小時 | 法定下限 | 勞基法第 34 條（輪班換班間距）。 |
| H5 連續上班 ≤ 6 天 | **院內政策（比法規更嚴）** | 勞基法第 36 條為「每七日一例假」；醫療業於變形工時制度下，合法連續上班可能超過 6 天。本平台採更嚴格的固定上限作為預設治理政策。 |
| H6 週工時 ≤ 60 小時 | **院內政策（簡化模型）** | 勞基法第 32 條規範的是延長工時上限，非單週總工時常數。60 小時為「正常 40 ＋ 延長 20」的簡化絕對上限。正式導入時應依院方適用之（二週／四週／八週）變形工時制度重新定義。 |

> 對外簡報時：H4 可稱法定下限；H5、H6 應稱「以法規為底線、比法規更嚴的院內治理政策」。

## 單位人力與護病比

`UNIT_MIN_STAFF` 定義各單位每班別的**最低配置人力**；主管確認摘要會顯示
「目前在班 → 替補後」與配置的比對，替補後仍不足時列入人工確認事項。
本 demo 的班表是單位的**部分名單**，故最低配置以 1 計，用來呈現判定機制本身；
正式導入時應對接院內護病比（nurse-to-patient ratio）與實際配置人數，
並將「替補後單位人力仍不足」升級為明確的風險標記。

## 決策留痕的防竄改

留痕採**雜湊鏈結**（每筆紀錄的雜湊包含前一筆的雜湊），事後修改任一筆
都會使後續整條鏈驗證失敗；匯出檔含 `chainValid` 驗證結果。
此為前端 demo 可誠實實作的 tamper-evident 機制；正式導入時由後端以
append-only 方式儲存，雜湊鏈可保留作為跨系統核對的輕量證據。

## 多筆缺班的指派語義

- **逐筆指派（貪心，對照組）**：依缺班順序每筆取當下最高分候選並立即寫回模擬班表。
- **全局指派**：枚舉所有可行組合（每筆可指派或留空），目標為字典序最佳化——
  **先「填補筆數最多」、再「總分最高」**；同分取先枚舉之組合（結果確定性）。
- 組合可行性以完整模擬驗證：同一人接多筆時，前一筆寫回後會影響後一筆的
  H2／H4／H5／H6 判定與評分（工時、公平性累計）。
- 規模聲明：demo 為 11 人 × 少量缺班，暴力枚舉即為最佳解；正式導入若缺班筆數
  放大，應改用匹配／整數規劃求解器，目標函數不變。
- 指派結果是**建議**：仍需主管逐筆確認後才寫回正式班表。

## 班表生成的語義（第 0 層：源頭治理）

- **定位**：缺班處理階梯（下節）的上游。把同一套規則放進排班源頭，
  讓班表「排出來的那一刻」就合規——下游各層被觸發得越少越好。
- **硬性約束**：與缺班替補**同一份 `checkHardConstraints` 程式碼**、同一份規則庫參數。
  規則調整後重新生成即生效；生成與替補的判定不可能不一致。
- **邊界條件**：既有班表整份注入。上一週最後一日的大夜殘影（H4）、
  跨週的連續上班天數（H5）都會約束生成；自然週工時（H6）依每格日期所在週各自計算。
- **排序目標**（生成專屬的公平性，全部確定性）：本次生成班數最少者優先（總量均衡）
  → 該班別被排次數最少者優先（夜班等輪值均衡）→ 意願相符 > 未表態 > 不符
  → 代號字典序（同輸入必得同班表）。
- **誠實原則**：排不出的格子不硬塞、不放寬——逐格彙整「各規則擋下幾人」交主管決策。
- **雙重驗證**：逐格檢查之外，生成結果疊上現有班表後以主動預警掃描器（M2）整表重掃，
  與生成前比對——新增「已違規」必須為 0，新增「達門檻／接近門檻」如實列出。
  兩條檢查路徑互相印證。
- **公平性分佈**（最多／最少班數）只計「整週至少有一格合格」者；
  證照過期等整週不合格的人本來就排不進來，計入會誤導判讀。
- **生成結果是草稿**：不寫入正式班表。正式導入時由護理長逐格調整後發布，
  調整仍受同一套規則即時檢查；演算法為貪心＋確定性排序，正式導入若需求規模放大，
  應改用整數規劃求解器，目標函數與硬性約束不變。

## 能力徽章與帶班平衡的語義（★ 能力與出勤）

- **兩種徽章，兩個問題**：資格徽章（證照）回答「有沒有人會做」；
  進階徽章（臨床進階制度 N1 基礎照護 → N2 重症照護 → N3 整體照護與教學
  → N4 專案與研究；AHN 副護理長）回答「有沒有人扛得住」。
- **效期三態**：valid／expiring（基準日起 90 天內到期，視窗可調）／expired。
  **過期即不計入戰力**——單點依賴與覆蓋計算一律排除過期證照。
- **帶班資深門檻**：預設 N3 以上（院內政策，`seniorLevel` 參數可調）。
  「三班實力平衡」的檢查點＝每一個有排班的班別，班上至少一位達門檻者。
- **單點依賴**：某資格的有效持有人 ≤ 1 即單點故障訊號——該員倒下，
  此能力就從單位消失（第三層韌性模式劇本的前兆指標）。
- **資格×班別覆蓋**以「該班別有排班的天數」為分母，不把空班算成未覆蓋。
- 出勤與公平為單週快照；正式導入後累積為趨勢（離職螺旋的前導指標）。
- 進階層級未評級者（無 ladder 欄位）以 0 級計、誠實標示「未評級」，不臆測。

## 排班工作區的語義（畫面 5）

- **三種放班表的方式，一個班表**：格子點擊編輯（無→白→小夜→大夜→清除）、
  Excel 貼上匯入（每列＝代號＋七欄班別；Tab 分隔保留空欄）、
  套用第 0 層生成草稿。三者寫入同一份班表，缺口總覽與主動預警即時重算。
- **持久化邊界**：排班工作區的變更（編輯／匯入／套用）保存在本機 localStorage；
  「主管確認寫回」維持演示語義——不保存、重新整理即重置。
  載回時逐筆白名單驗證（代號、日曆日期、班別、單位），不合法項目直接剔除。
- **匯入的誠實原則**：整列有任何無法辨識的值，該列**整列不套用**並逐列報告原因
  ——寧可少排，不套用可疑資料。匯入只取代「列出人員 × 該週」的班次，其他人不動。
- **留痕**：每一次編輯、匯入與套用都寫入決策留痕（改了誰、哪一天、從什麼改成什麼）。
- 編輯不自動重算進行中的缺班評估（與「已結案事件不可變」同一哲學）；
  條件改變由主管回「缺班事件」重新確認。

## 人力缺口分析的語義（管理總覽）

- **缺口方程式**：營運所需人力 −（已排定 ＋ 可合法吸收）＝ 殘餘缺口。
  實作為 `workforceGapAnalysis`，對每個「單位 × 日期 × 班別」計算。
- **需求基準**（demand）由外部注入，demo 以各班別最低安全配置（`UNIT_MIN_STAFF`）計；
  正式導入應對接護病比與各單位實際營運需求，且基準本身可依規則庫調整。
- **吸收模擬**分兩道：先同單位人員、再加入熟悉此單位的跨單位人員——
  用**同一份 `checkHardConstraints`**逐格驗證，填補逐格寫入工作副本
  （同一人不會被重複計算為兩格的吸收量）。每筆可行填補附風險標記（F 系列），
  即「可行，但有代價」。**可吸收 ≠ 建議照做**，決定權在主管。
- **殘餘缺口**誠實保留，逐格標示各規則擋下幾人（與班表生成同一種缺格語義）。
- **結構性缺口**：同一單位同一班別在區間內出現缺口 ≥ 3 天（`structuralDays` 參數）。
  結構性缺口的意義：反覆靠替補補洞不是解方，應回到源頭
  （第 0 層班表生成／招募員額／夜班培訓）。
- **資料誠實**：完全沒有排班資料的單位回報 noData、不列入計算；
  部分名單單位的數字標示為機制展示，不進主敘事。
- demo 為單週快照；正式導入時缺口紀錄應持續累積，
  作為招募員額、預算編列、跨院區支援與培訓規劃的依據。

## 任務重分配的語義（第三層：韌性模式）

缺班處理是**從源頭到韌性的決策階梯**：

```
第零層：班表生成（generateSchedule）─────── 源頭治理：排出來就合規
第一層：找合格替補（evaluateGap）────────── 有人 → 結束
第二層：放寬試算（relaxationAnalysis）＋全局指派 ── 主管核准後有人 → 結束
第三層：任務重新分配（reallocateTasks）──── 缺的不再是「一個人」，是「一班的任務」
```

- **輸入**：缺班者任務清單（任務 × 必要資格 × 工作量點數 × 是否關鍵）、
  在班人員（含資格）、每人可多承接的負荷上限。資料全部由參數注入（純函式）。
- **演算法**與全局指派同宗：枚舉全部可行組合，字典序最佳化——
  未覆蓋關鍵任務數最少 → 未覆蓋總數最少 → 最大個人負荷最小（平衡）→ 同分取先枚舉者。
- **資格是硬性條件**：需特定資格的任務絕不指派給無資格者，寧可標示缺口。
- **誠實原則**：系統不自動刪任務、不自動降載。無人可承接的任務逐筆標示原因
  （`no_qualified` 無人具資格／`over_capacity` 量能不足），連同建議決策選項
  （上報院級調度、跨區支援、非緊急任務延後）交主管決定。
- 本版為獨立演示情境（`TASK_REALLOC_SCENARIO`）；正式導入時任務清單應來自
  護理排程／醫囑系統，負荷點數對接院內護理時數評估工具。

## 個人限制的語義（H10：母性保護等）

- **登錄位置**：人員主檔 `staff.restrictions`，每筆 `{ from, to, shifts, reason }`；
  期間判定**含首末日**（`from <= 日期 <= to`），班別以受限清單逐一比對。
- **粒度聲明（誠實邊界）**：示範以「班別」為粒度。勞基法第 49 條禁止的是
  **22:00 至翌晨 6:00 的時段**——大夜（23–07）全落在禁止時段，小夜（15–23）的
  最後一小時亦跨入。正式導入應以時段判定，並將小夜納入評估；示範資料
  僅標大夜，於規則描述中如實聲明。
- **作用範圍**：與其他硬性約束同一份 `checkHardConstraints`——替補評估、
  換班簽核預檢、班表生成三處自動套用；已排定班次落在限制期間者，
  由主動預警以 high 等級揭露（不是風險，是現在就違法）。
- **不可放寬**：H10 屬法定禁止與醫囑限制，`relax.allowed = false`；
  放寬試算不會提供停用選項的建議，人力不足應改走任務重分配。

## 主動預警的語義

對**已排定的班表**做靜態掃描（不涉及任何缺班事件），分三個等級：

- **high（已違規）**：班表本身已牴觸硬性規則（如相鄰班次間隔不足 11 小時、連續超過上限）。
- **medium（達門檻）**：再多排一步即違規（連續天數達上限、當週工時達軟性上限、公平性達飽和）。
- **low（接近門檻）**：距門檻一步之遙（如再被叫班一次即達飽和）。

門檻一律取自規則庫的同一份參數（H4／H5／H6／S1／S2），規則調整即時反映。
配置缺口掃描以單位為單位彙整；**完全沒有排班資料的單位回報 noData 而非整週缺口**
（示範資料為部分名單，避免誤報）。

## 公平性訊號

`standbyCount30d`（近 30 天被叫班次數）在本版為**靜態快照的代理指標**：寫回時 +1，
但不會隨時間滾動過期。正式導入應定義為「以院內實際叫班紀錄計算之滾動 30 天窗口」。
S1 飽和門檻（預設 5 次）意義：達此次數者公平性得 0 分，優先保護已被頻繁叫班的人。

## 缺班事件生命週期

```
草稿（解析中） → 已確認條件（評估中，可重算、可換人選） → 已結案（主管確認、已寫回）
```

- **已結案的事件是不可變的**：不得重新選人、不得重算——替補班次已寫回班表，
  重算會讓剛指派的人被 H2 排除，產生「已補完卻顯示缺口」的矛盾。
- 結案後的規則調整仍會儲存，**套用於下一筆缺班評估**。
- 要重新評估，回「缺班事件」頁重新確認條件，即建立新的評估。

## mock 解析的能力邊界（不臆測原則）

mock 模式以關鍵詞規則比對訊息，**只回報有依據的欄位**，其餘轉為追問：

- 日期：支援「今天／明天／後天」「M/D、M月D日」「（下×N）禮拜／週／星期＋X」
  （每一個「下」往後一週：下下禮拜三 = +14 天）。無法明確換算的說法（「這週末」「連兩天」）→ 追問。
  訊息中出現**多個時間線索且指向不同日期**（例：「從今天開始發燒，禮拜天的班……」）→
  不挑選其中一個，標記為模糊、轉為追問，並列出偵測到的所有線索。指向同一天則正常解析。
- 班別：白班／早班／日班、小夜／晚班、大夜／夜班。
- 事由：病假、進修、事假、特休關鍵詞；無線索時記為「臨時請假」（唯一有預設值的欄位）。
- 單位與必要資格：僅在訊息明確提及時抽取，否則一律追問。

模型（mock 或 api）**永遠不做**：補完缺漏欄位、改寫引擎算出的數字、放寬規則、代替主管決定。

## 引擎介面

引擎以 `createEngine(db)` 建立，人員／班表／班別／職級／規則全部由外部注入，
引擎內不讀取任何全域資料。注入的是同一份參照：規則庫調整與寫回即時生效。
同一份 `src/engine.js` 在瀏覽器（index.html）、測試（tests.html 與 CI 的 Node runner）
與未來的 Lambda 端點上運行，行為必須一致——這由 `tests/engine.test.js` 保證。
